# 基本概念

## 聚合、广告位、广告源

你的 App 里有一个广告展示机会，但你不直接对接广告主。你需要通过**广告平台**来**填充这个位置**。**聚合**要解决的问题是：**同时对接多家广告平台**，让每一次展示机会都能卖给**出价最高或最匹配**的那一家。

**广告位**

**在聚合平台后台创建**广告位，然后在**外部广告平台创建应用和广告位**，拿到**广告位 ID、APP ID、APP Key** 关键信息，然后在聚合平台把这些信息填入对应应用的广告位，要注意**聚合平台和广告平台配置的广告类型要一致(如都是激励视频类型)才能绑定**。

**广告源**

是开发者在第三方广告平台创建的广告位。广告源在聚合平台里，本质上是你绑定到某个广告位上的一家外部广告平台的“销售通道”，**广告位是你自己定义的“坑”，广告源是填进这个坑的“外部供给”**。

**聚合(Mediation)**

核心机制是**瀑布流(Waterfall) 或 竞价(Bidding)**。

Waterfall 按你预设的 eCPM 顺序逐个请求广告源，谁先接受就展示谁。

Bidding 则是让多个广告源实时竞价，价高者得。Bidding 模式通常能提升填充效率和 eCPM，因为它减少了因“顺序试探”而浪费的请求。

## 聚合平台和广告网络的关系是什么

**广告网络**手里有广告主的钱和订单，**促成流量主与广告主之间的广告交易**。

**聚合平台**手里没有广告订单，它有的是大量 App 的广告位，帮开发者把多家广告网络的库存接进来、实时比价，提升广告 ​eCPM 和整体填充率。

|       | 广告网络(Ad Network) | 聚合平台(Mediation)       |
| ----- | ---------------- | --------------------- |
| 核心资产  | 广告主预算、广告订单       | 开发者的广告位、多家广告网络的接入     |
| 回答的问题 | “谁来出钱买这个展示？”     | “这次展示卖给哪一家出价最高？”      |
| 收入来源  | 广告主支付的广告费        | 从广告费中抽取的差价(take rate) |

聚合平台和广告网络是**两层独立的 SDK，中间有一层适配器(Adapter)来桥接**，聚合平台本身并不“生产”广告，它是一层**调度和统一接口**；真正去请求、拉取并渲染广告素材的，仍然是各个广告网络自己的 SDK。

**适配器**是**聚合平台为每一家广告平台**写的一层“翻译桥”。它的作用是：聚合 SDK 发出一个统一的“加载广告”指令，适配器把这句指令**翻译成**目标广告平台 SDK 能听懂的 API 调用；广告平台返回素材后，适配器再把结果**翻译回**聚合 SDK 能理解的格式。

## 广告类型

**开屏广告**  
你**打开 App 的瞬间**，全屏出现的广告。比如你点开一个游戏，在加载界面那 3–5 秒里，整个屏幕是一张品牌海报或一段短视频。它的特点是**强曝光、被动触达**，几乎每个启动用户都会看到，所以 eCPM 通常较高，但用户没有选择权。

**激励视频**  
用户**主动选择**观看一段 15–30 秒的视频，换取一个明确的回报。比如游戏里角色死亡后，屏幕上出现两个按钮：“看视频复活”或“放弃”。用户点了“看视频”，完整看完后获得一次复活机会。因为用户是自愿投入注意力的，广告主的转化预期最强，所以**激励视频的 eCPM 在五种类型中通常最高**。

**插屏广告**  
在**自然的流程节点**弹出，打断当前操作。比如游戏一局结束、进入结算页面之前，弹出一个全屏广告。它占据强注意力位置，但用户是被动接受的，体验侵入性比开屏更强，所以**频率控制很关键**。**常见于“暂停”“退出”“关卡切换”等时刻**。

**原生广告**  
广告**长在内容流里，看起来像 App 本身的一部分**。比如在一个资讯流或关卡列表里，第三条“内容”实际上是一条广告，但它的排版、字体、图片风格和你 App 的内容几乎一致。用户干扰度低，但需要你（或 SDK）做自渲染，把广告样式融入你的 UI，**eCPM 通常低于激励和开屏**，但可以高频展示而不太破坏体验。

**Banner（横幅）**  
一条**细长的通栏广告，固定在页面顶部或底部**。比如游戏主界面的最下方，始终挂着一条高度约 50–100px 的横幅。它持续可见但注意力分散，用户很容易“视而不见”，**eCPM 是五种类型中最低的**，但它几乎不打断操作，可以作为持续性的底仓收入。

**激励视频的 eCPM 最高**，因为它是用户**主动选择观看**的：用户用一段时间换取游戏内奖励，完播率高，广告主知道这条曝光触达的是一个有意愿、有注意力的用户，因此愿意出更高的价格。**开屏和插屏的 eCPM 次之**，它们占据的是强注意力位置（启动瞬间、内容切换点），但用户是被动接受的。**Banner 和原生**通常 eCPM 最低，因为它们融入内容流，注意力分散，转化意图弱。

一个常见的模式是：**开屏贡献最大的收入占比，激励视频贡献最高的单价，而原生和 Banner 的 eCPM 处于低位**。

## 基础概念总结

关键关系一句话：**你在自己的 App 里创建“广告位”（库存），用“聚合”去管理多个“广告源”（外部进货渠道），而每个广告位最终以某一种“广告类型”呈现给用户。**

## 一次广告展示，钱和决策是怎么流动的

1. **广告主**有产品要卖，把预算交给**广告网络**，由后者代表需求方去寻找合适的展示机会。
2. 当用户在你的 **App** 里**进入一个广告位**，**广告 SDK** 触发一次广告请求。这个请求会经过**聚合平台**，聚合平台同时向多家接入的**广告网络**询价，把这次展示**卖给出价最高**的那一家。
3. **广告网络**拿到**展示机会**后，从自己的**广告主池中匹配一条广告**返回，**SDK 负责渲染展示**。用户看到广告，广告主为此付费；钱从广告主流向广告网络，广告网络结算给聚合平台，聚合平台再结算给 App 开发者。

## 核心效果指标：广告变现的“仪表盘”

**ROI（投资回报率）**
含义：**净利润 ÷ 投资成本**，衡量的是“这笔生意最终赚了还是亏了”。公式：`(总收入 − 总成本) ÷ 总成本 × 100%`。它要扣掉广告花费之外的运营、人力等成本，是**生意层面的指标**。

**ROAS（广告支出回报率）**
含义：**广告带来的收入 ÷ 广告花费**。**ROAS = 120%**——每花 1 美元广告费，这些用户产生了 1.2 美元的广告收入。ROAS 只看广告费，不看其他成本，所以它比 ROI 更“薄”，是买量团队每天盯的优化指标。

**IAA（In-App Advertising，应用内广告）**  
含义：**通过在你的 App 里展示广告来赚钱**，而不是让用户付费。用户免费使用 App，通过看广告变现。

**CPI（每次安装成本）**  
含义：**买一个用户安装你的 App，平均花多少钱**。公式：`广告总花费 ÷ 安装总次数`。它是买量的“进货价”。

**ARPU（每活跃用户平均广告收入）**  
含义：**一个活跃用户平均给你带来多少广告收入**。公式：`广告变现收入 ÷ 活跃用户数`。它是买量回本计算里最直接的“分子”。

**eCPM（每千次展示的有效收入）** 
含义：**每卖出 1,000 次广告展示，平均能收多少钱**。公式：`(广告收入 ÷ 总展示数) × 1000`。它衡量的是库存的“单价质量”。

**ADPV（广告曝光数）**  
含义：**一段时间内，广告实际被用户看到了多少次**。它是收入公式里的“数量项”：`收入 ≈ ADPV × eCPM ÷ 1000`。

**AIPU（人均广告展示次数）**  
含义：**平均每个活跃用户看了多少次广告**。公式：`总广告展示数 ÷ 活跃用户数`。它可以进一步拆成：`人均广告请求数 × 填充率 × 展示率`。

**广告渗透率**  
含义：**活跃用户中，有多大比例至少看过一次广告**。公式：`产生广告展示的用户数 ÷ 活跃用户数`。渗透率低，说明大量用户完全没有被广告触达，AIPU 的上限也会被压住。

**关联关系：**
渗透率决定“多少人被触达”，AIPU 决定“每人看几次”，两者相乘得到 ADPV；ADPV 乘以 eCPM，决定 ARPU；ARPU 与 CPI 相比，决定买量的 ROAS 能不能站住。

# 买量
## 什么是买量

**买量**就是花钱从广告平台（Google Ads、Meta、TikTok 等）购买用户安装。你为每一次安装支付一个 **CPI**，用户装上你的 App 之后，通过看广告（是广告变现模式，不是用户付费模式）为你产生收入。

衡量这笔买卖是否划算的核心指标是 **ROAS**：

ROAS = 广告带来的收入 ÷ 广告花费 × 100%

## 为什么买量成本升高后，要“换 App”

**买量不是静态的**。你在一个 App 上持续投放，会逐渐遇到两重压力：

第一，**竞价环境在变贵**。当更多广告主同时争夺同一批用户时，CPI 会被推高。这不是你的产品变差了，而是获客的“进货价”上涨了。

第二，**你的 ROI 分母在变大**。ROAS = 收入 / 花费。如果 CPI 上升，而单个用户的广告 ARPU 没有同步上升，ROAS 就会从 120% 向 100% 甚至更低滑落。一旦跌破 100%，买量就从“赚钱”变成“烧钱”。

 IAA 驱动的产品结构下，单产品优化有天花板。广告 ARPU 的提升受限于广告位数量、用户观看意愿和 eCPM 水平；而 CPI 的上涨是外部市场力量，你很难单方面压回去。当两者之间的利润空间被压缩到不可接受时，**继续在同一个 App 上加预算，只会放大亏损**。

换一个新的 App 重新买量，逻辑不是“新产品一定更好”，而是**用一个新的定价环境重启一次 ROI 计算**。新 App 在上线初期，往往能以相对较低的 CPI 获取第一批用户——因为它还没有进入同一个竞价池的“成熟期成本结构”。

# 马甲包
## 什么是马甲包

“马甲包”（Cloned App / Rebranded APK）指的是在原有 App 的基础上，仅更换**应用名称、图标、包名、UI 皮肤或部分功能模块**后，重新打包上架的“衍生版本”。它们的内核代码和核心功能往往高度相似，只是披上了不同的“马甲”。

## 为什么会有“马甲包”这种业务模式

核心驱动力是**商业利益最大化**。

1. **最大化流量与曝光**：这是最直接的动力。每个 App 在商店中可覆盖的关键词有限，上架多个马甲包意味着可以**覆盖 N 倍的关键词**，从而在更多搜索结果中获得展现，触达更广泛的潜在用户。同时，多个包之间可以相互导流，为主包“输血”。
    
2. **风险隔离与“背锅”**：将马甲包视为“试验田”或“防火墙”。新功能、有风险的操作（如刷榜、机刷）可以优先在马甲包上测试。一旦某个包因违规被下架或处罚，主包和其他马甲包的业务不受影响，起到了风险缓冲的作用。
    
3. **低成本测试与优化**：通过多个马甲包并行运营，可以低成本地进行 **A/B 测试**，对比不同UI、图标、名称对用户转化率的影响。某个马甲包的成功经验可以反哺主包。
    
4. **多品牌与区域化布局**：为不同国家、语言或用户群体创建定制化的版本，实现更精细的市场覆盖。或者，针对同一功能建立多个品牌，以占据不同的用户心智。

哪个包能以更低的成本拉到用户、哪个包的广告 ARPU 跑得更高，就把买量预算集中到哪个包上。当某个包的 ROAS 衰减到不再值得加预算，就把它维持在自然量状态，用一个新的包去承接下一轮买量。马甲包在这里承担的角色不仅是“换皮”，更是**风险隔离和快速试错的载体**：一个包的模型衰减或违规，不直接拖垮整个产品矩阵。

## 为什么 GP 要封禁马甲包

Google Play 的《开发者计划政策》明确**禁止重复内容**和**欺诈行为**。平台认为，上架大量功能雷同、仅换皮的应用会**损害用户体验**（充斥同质化应用）、**扰乱商店生态**（挤占搜索资源），并可能被用于**欺诈**（如虚假导流、刷量）。因此，一旦被判定为马甲包，Google 会将其视为违规，可能导致**所有关联应用被下架**，甚至**开发者账号被永久封禁**。

Google 的检测已非常成熟，会综合**代码相似度（如超过 85% 即高危）、开发者账号关联（IP、设备、付款方式）、用户交叉数据**等多维度进行识别。即使你试图通过**多个开发者账号**来发布这些马甲包，Google 强大的**账号关联封禁系统**也会构成巨大障碍。平台会通过**注册资料、收款账户、登录设备、IP 地址**等数十个维度来判断账号间的关联性。一旦其中一个账号因马甲包违规被查，**所有与之关联的账号都可能被“连坐”封禁**。

Google Play 允许一个开发者账号发布多个应用，但前提是每个应用都必须提供**独立的、有价值的用户体验**。

## GP 账号本身有 App 数量限制吗

个人开发者账号在政策上通常被限制发布 **20 个**应用；组织（企业）账号则**没有明确的应用数量上限**。此外，Play Console 在操作层面有一个上传频率限制：**每 24 小时最多 15 个**应用。**“没有上限”不等于“可以无限铺”**。Google 的风控系统会把一个账号下 App 数量过多、上传行为密集的情况标记为“批量操作”，封号概率会显著上升。

# 竞价广告源和常规广告源加载流程

核心不是「竞价源永远优先」，而是：**先询价，再用价格插回瀑布流一起排**。

一次 `load` 大致是：

1. SDK 向所有头部竞价广告源**同时询价**（**只问价，还不一定去拉素材**）
2. 各竞价源返回实时 eCPM；常规源用你在后台填的排序价格（固定价）
3. 两类价格混在一起，从高到低排序 → 得到本轮最终瀑布流
4. 按这个顺序请求（串行，或并行 N 条）
5. 展示时选已返回广告里排序价最高的那条（不是“谁先返回就展示谁”）

- 优先级 = 本轮 eCPM/排序价高低，不是「竞价 > 常规」硬规则。
- 竞价源的特点是：每次价格可变；常规源是：价格写死在后台。
- 「竞价次数高、展示率低」很常见：高价常规层先填满了，竞价源只询了价、没轮到请求/展示。

先并行询价 Bidding → 用价格和常规源混排 → 再按混排结果（默认串行）请求；配置列表顺序不重要，价格才重要。

# 服务端竞价 vs 客户端竞价

|        | 客户端竞价 (C2S)                              | 服务端竞价 (S2S)                       |
| ------ | ---------------------------------------- | --------------------------------- |
| 询价路径   | TopOn SDK → 各 ADN SDK → ADN 服务器          | TopOn SDK → TopOn 服务器 → 各 ADN 服务器 |
| 比价发生地  | 手机端（SDK 本地）                              | TopOn 服务器                         |
| 集成感    | 更直接，走各家 SDK 询价接口                         | 对开发者更省心，很多对接在服务端                  |
| 特点     | 受端上网络/机型影响更大，策略改动偏慢                      | 延迟通常更稳，策略可在服务端调                   |
| 谁决定用哪种 | 看广告平台支持什么；有的两家都支持（腾讯/快手/Sigmob 等），后台勾选即可 | 同左                                |

对你日常运营：后台勾「头部竞价」+ 选 C2S/S2S，**本质是换询价通道**；**混入瀑布流后的排序、请求、展示规则是一样的。**

# 各 ID 的含义和关系是什么

- **场景 ID**：App 里的业务入口标签（签到、通知开屏…）。多个场景可以挂同一个聚合广告位，用来拆展示/点击漏斗；不能精确拆真实收益。
- **聚合平台广告位 ID**：真正决定怎么卖这次展示的单位。一个 ID 对应一套瀑布流 + 竞价配置；收益按它统计。
- **广告源**：挂在该聚合广告位下的一条「外部通道」（Meta 竞价 / AdMob 分层 20…）。
- **广告源平台后台广告位 ID**：那条通道真正去请求时用的三方代码位；聚合后台只是把它绑到某个广告源上。类型必须一致（都是激励视频等）才能绑。

# 从触发场景到广告展示的流程是什么

单聚合（TopOn / Max / AdMob）已经是在多家广告网络之间调度。  
混聚合（Hyperbid 三方 / Flynk 自建）再往上一层：把多个聚合平台的广告位当成自己的“广告单元”，再比一次价。
 
混聚合是「聚合的聚合」，用来在 TopOn/Max 等之间再比一次或做主备；怎么选取决于比价还是瀑布流配置。

混聚合下多家单聚合有 2 种模式：

- 比价：多家都会请求，再比价展示。
- 瀑布流：按优先级，够缓存了才停后面的聚合。

场景触发 → load 聚合广告位 → 拉策略
    → Bidding 询价（只要价，一般还不算填充）
    → 按价格混排
    → 轮到某广告源：适配器调 ADN SDK 发广告请求
    → ADN 服务器返回广告内容          ← 填充发生在这里
    → ADN SDK 通知聚合 SDK：广告就绪（isReady / onAdLoaded）
    → 业务 show → 用户看见              ← 这才是展示
