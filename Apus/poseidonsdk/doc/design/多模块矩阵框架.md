# 多模块矩阵框架方案评估

## 方案概述
1. 将现有混聚合广告 SDK 拆分为若干独立子模块（如 AdMob 聚合封装、广告比价、初始化、预加载等），模块间通过稳定接口耦合。
2. 每个子模块制作 10 套功能等价但代码实现低相似度（<30%）的版本。
3. 把这 10 套实现以独立版本的 AAR 上传至 Maven 仓库（例如 `ad-preload-v1a` ~ `ad-preload-v1j`）。
4. 新建 SDK 时，通过组合不同模块的不同变体来拼装完整能力，形成自然差异。
5. 对产出的 SDK 再统一执行字典混淆、等价代码替换等步骤，保证 API 命名和符号独特。

## 整体评价
- **可行性**：通过模块化 + 变体矩阵可以实现大量低相似度 SDK，且避免为每个 SDK 重写全部逻辑。关键是模块接口需高度稳定，组合时保持配置兼容。
- **维护性**：比“全量重新生成”方案更好，SDK 只是引用不同依赖组合；但每个模块同时维护 10 套实现仍有较大成本，建议引入 AST/字节码生成器自动产出变体，并使用统一测试套件保证一致性。
- **风险点**：
  - **版本爆炸**：模块数量 × 10 变体会导致依赖管理复杂，需要版本矩阵系统和自动化构建脚本。
  - **同步更新难**：同一功能修复必须同步到 10 套实现；需要自动化同步工具或共享内核 + 差异化壳层方式降低重复劳动。
  - **组合冲突**：不同模块变体可能在线程模型、配置约定上冲突，需定义严格的接口契约与兼容矩阵。
- **改进建议**：
  1. 使用 DSL 描述模块依赖与组合约束，生成 Gradle 依赖图。
  2. 对 10 套变体采用自动化生成/转译，让核心逻辑只维护一次。
  3. 在 CI 中增加 SimHash/AST 检查、自动化回归，确保低相似度与功能一致。
  4. 建立版本与依赖管理平台，追踪模块变体的组合关系，减少维护盲区。***
