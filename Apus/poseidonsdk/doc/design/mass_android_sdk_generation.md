# 大规模低相似度 Android 混聚合广告 SDK 方案设计

## 背景与目标
- 在 1~2 周内交付 100 个业务逻辑复杂、具备统一能力基线的混聚合广告 SDK。
- 每个 SDK 需要独立的包名、对外 API 命名空间、接入指引、文档与版本号。
- 任意两个 SDK 的代码相似度需 <30%，同时仍可共享核心投放策略、监控体系与运营能力。
- 方案需保证长期可扩展，可持续生成新的 SDK，并能在不同客户与行业场景下快速定制。

## 设计原则
1. **模板化 + 参数化**：抽象可复用的业务内核，所有差异化信息来源于结构化配置/DSL。
2. **模块化可选**：通过策略插件、渠道适配器、数据管线等模块的组合/替换制造结构差异。
3. **代码变体自动生成**：借助代码生成器和语义保持的重写器控制 API 命名、类层次与实现细节。
4. **资产分层**：内核服务（算法、策略、监控）与 SDK 壳层隔离，壳层负责对外形态与差异。
5. **工程自动化**：流水线化拉取模板 -> 生成 -> 构建 -> 自动测试 -> 交付，避免手工操作。
6. **可验证性**：全链路测试、签名、灰度与监控可证明每个 SDK 质量可控。

## 总体架构
```
需求配置中心
      │
      ▼
SDK 生成编排服务 ────► 模版引擎 (Gradle project templates)
      │                        │
      │                        ├─ DSL/配置覆写器
      │                        └─ 变体生成器 (结构/命名/控制流)
      │
      ├─► 代码多样化服务 (AST/字节码层变换、模块排列)
      ├─► 依赖镜像仓库 (渠道适配器、策略插件)
      ├─► 自动化构建集群 (Gradle + AGP)
      ├─► QA 流水线 (静态扫描、UT、合成流量测试、性能/稳定性)
      └─► 可观测性接入 (A/B 配置、埋点模板)
```

- **内核服务层**：由 poseidon 现有投放/策略/数据同步模块组成，作为 AAR/动态 Feature 模块供所有 SDK 引用。
- **外壳 SDK**：每个 SDK 单独的 Android Library 项目，包含 API、渠道编排、UI、配置、文档。
- **控制中心**：统一的 DSL（YAML/JSON/Proto）描述客户定制需求、渠道组合、策略开关、品牌信息。

## 模型与 DSL 设计
```
sdk_spec:
  id: voyager_xxx
  package: com.customerX.ads
  api_surface:
    entry_points:
      - name: VoyagerAds.initialize(...)
      - ...
  monetization_mix:
    - channel: meta
      adapter_variant: b
    - channel: tt
      adapter_variant: e
  strategy_profile: high_ctr
  feature_toggles:
    use_ai_bid: true
    enable_stream_batch: false
  customization:
    ui_theme: neon
    proguard_profile: type_b
    naming_set: greek_letters
```
- DSL 与模板引擎驱动项目骨架（Gradle settings、模块/源集、Manifest）。
- `naming_set` 与 `api_surface` 控制命名空间、注释、KDoc 等差异化素材。

## 代码多样化策略
1. **模块层面**
   - 渠道适配器矩阵（Meta/TikTok/快手/穿山甲等）提供 ≥3 个实现版本：标准、轻量、带缓存。
   - 数据上报、缓存、合规处理模块提供不同的 pipeline 布局（串行/并行/分区），组合即形成拓扑差异。
2. **结构化差异**
   - 通过 AST 生成器随机化类层次（例如策略上下文类拆分为多个 partial 类）、接口 vs 抽象类等结构。
   - 切换 RxJava/Coroutine/自研协程封装，形成并发模型差异。
3. **代码语义保持重写**
   - 模板内置多套算法实现（如竞价加权、频控缓存）并通过 DSL 选择。
   - Bytecode/Source 级重写器进行命名置换、控制流平坦化、常量表拆分，保证测评工具难以判断相似度。
4. **资源层差异**
   - 不同的 assets、UI、配置文件结构（如 JSON vs Proto）。
5. **构建与发布差异**
   - Gradle 插件自动生成 unique build flavor、签名文件、ProGuard mapping，从产物层面进一步区分。

## SDK 生成流水线
1. **配置收集**：产品、运营在需求管理系统中提交 `sdk_spec`，进入编排队列。
2. **模板实例化**：
   - 选取基础模板（场景：无 UI / 内嵌 UI / 全屏弹窗）；
   - 注入 DSL 配置，生成 Gradle project skeleton。
3. **模块装配**：
   - 根据 `monetization_mix` 和 `strategy_profile` 拉取对应版本的渠道适配器、策略插件；
   - 通过 module graph solver 计算依赖并写入 `settings.gradle`、`build.gradle`。
4. **多样化变换**：
   - AST 工具链二次遍历以生成命名/结构变体；
   - 植入差异化的日志标签、埋点 ID、注释。
5. **构建与测试**：
   - 统一 CI 触发 `./gradlew lint test assembleRelease`;
   - 运行仿真端到端流量脚本验证聚合策略、竞价节奏、SDK 初始化性能；
   - 产出报告（覆盖率、性能、包体积）。
6. **签名与交付**：
   - 生成客户独立签名/keystore；
   - 自动生成集成文档（含 Maven 坐标、ProGuard 配置、权限清单、初始化示例）；
   - 上传制品至私有 Maven 仓库，并通过版本管理平台通知客户。

## 测试与质量保障
- **静态分析**：禁用危险 API、隐私扫描、相似度基线检测（SimHash/AST diff 确保<30%）。
- **单元测试**：策略引擎、竞价排序、缓存一致性。
- **组件化合成测试**：使用统一的 Mock 媒体与聚合服务器进行自动化回归。
- **性能/稳定性**：冷启动、首次请求延迟、内存占用、ANR、崩溃率。
- **真实设备抽检**：CI 自动下发至设备云，覆盖主流 ROM/ABI。

## 运维与版本管理
- **版本矩阵**：每个 SDK 建立独立的语义化版本，使用 release board 映射到内核版本与渠道适配器版本。
- **补丁策略**：安全/合规缺陷由内核 hotfix 触发重新生成全部受影响 SDK，并保留自动化回归结果。
- **监控与回传**：统一埋点协议，SDK 初始化时上报自身 ID 与版本，使后端能关联流量表现。

## 安全 & 合规
- 集成隐私合规模块，支持动态配置权限申请策略。
- 为每个 SDK 生成独立的文档包，列出所用第三方渠道、数据加密、日志策略。
- 通过自动化脚本生成政策合规报告，降低人工审查成本。

## 人力与实施计划 (示例)
| 阶段 | 产出 | 资源 |
| --- | --- | --- |
| T0 + 2 周 | 模板与 DSL、三种策略插件、SimHash 相似度检测 | 架构 2、平台 3 |

通过以上体系，可在共享核心能力的前提下，稳定批量化产出满足低相似度、高质量要求的 Android 混聚合广告 SDK。***

，不过更完整：先用结构化 Spec 把每个项目的渠道组合、策略、API 形态、命名空间等定下来，然后由生成流水线产出 100 个独
立的 SDK。流水线除了生成“骨架”之外，还会在模块组合（不同适配器/策略实现）、架构层（并发模型、包结构）、资源/配置和命名层
都做差异化，再辅以特定混淆字典、等价代码替换、控制流重写等 AST/字节码层手段。这样每个 SDK 在保持核心能力一致的同时，整体
相似度就能低到 30% 以下，而不仅仅是简单“重写 + 混淆”。

但这个方案，每次有新加功能的时候，所有SDK都必须重写再实现一遍，所有SDK都必须重写打包，成本挺高的
确实如果直接“重新生成 + 重打包”100 次会很重。可以在方案里加入分层与可插拔的更新机制，把新增功能集中于内核层，SDK 外壳保持
轻量，只同步配置。关键思路：

- 内核模块化：把策略引擎、渠道适配器、监控等通用功能做成独立 AAR/动态 Feature，所有 SDK 只通过 Maven 依赖它们。新增功能
  时，只需更新内核版本并让 SDK 通过配置指向新的依赖，无需逐个改源码。
- 配置驱动：SDK 里用配置文件/远程开关控制功能开关，新增功能只需扩展 DSL & 生成的配置，客户端代码保持不动。
- 增量发布：流水线支持“批量 bump 依赖版本 + 自动回归 + 重新打包”，但这是自动化流程，不是手动重写；只对受影响 SDK 执行。
- 变体缓存：代码多样化步骤输出可缓存，新增功能时只在受影响模块上重新做 AST/混淆差异，剩余结构沿用旧版本，显著缩短耗时。
- 灰度/动态加载（可选）：部分新功能做成远程策略或动态插件（如通过动态 Feature/自研插件框架），SDK 仅需一次升级即可后续远
  程启用。

这样维护成本集中在核心模块和自动化流水线，而不是 100 个独立工程手工维护。

而且这个方案有个很大的问题是，每次都是全新生成新代码，可能导致逻辑复制的不一致性，从而导致后续自测和维护成本很高。

是，这种“全量再生成”会带来逻辑漂移风险。可以调整方案，让唯一可信版本集中在可复用内核，生成层只负责“包装”。建议补充：

- 共享内核 + 版本矩阵：策略/聚合逻辑只维护一套，可按版本号发 AAR。每个 SDK 的生成脚本只引用某个内核版本，包内不会复制逻
  辑。新增功能时升级内核版本并在配置中指向它，确保所有 SDK 逻辑一致。
- 生成层最小化：生成器只做命名空间、API façade、资源/配置等差异化，不真正复制业务逻辑。这样重生成时只需更新外壳，逻辑仍来
  源于同一内核。
- 自动验证：在流水线中加入 SimHash/AST 对比确认外壳与内核代码分离，且自测回归只针对内核模块为主，外壳做冒烟即可。
- 版本继承：SDK 生成脚本需要记录“内核版本 + 差异化策略”的元数据；当内核有新功能，脚本只是调度“更新依赖 + 再运行差异化流
  程”，不会复制代码块。
- 共享测试套件：保留单套 UT/集成测试覆盖内核，各 SDK 只跑自动化冒烟（初始化、渠道调度）。这样即便再生成，也不会重复维护
  100 套测试。

通过“内核统一、外壳差异化”的分层，可以满足低相似度要求，同时把维护与自测的成本集中在一处。
